## 二、TCX-Ⅱ-1：50节点单Raft组极限压测

### 2.1 测试配置
- 节点数: 50（单Raft组, Quorum=26）
- 资源限制: --cpus=0.25 --memory=256m 每节点
- 网络模式: Docker bridge (tcx2-50node)
- 镜像: raftkv-gateway:v22s
- 压测参数: 100并发 × 30秒 × 100%写入

### 2.2 测试结果
- **容器存活**: 50/50 全部存活 ✅（无节点掉线）
- **Leader选举**: ⚠️ 选举风暴，无法稳定选出Leader
  - 5个节点曾短暂当选Leader: N24, N26, N28, N30, N31（各1次）
  - term持续增长: 120→222→280+（30秒内增长160+）
  - 大多数节点leader字段为空（不知道谁是Leader）
  - N50的term=0（完全未参与选举，疑似资源不足）
- **gRPC压测**: TPS=689,037, 成功率=0%（无稳定Leader导致写入被拒）
- **延迟**: P50=0s, P99=2.52ms, P999=5.57ms, Max=2.70s
- **脑裂检测**: ✅ 无脑裂（没有多个Leader同时存在）

### 2.3 分析
50节点单Raft组在当前选举超时配置（150-300ms）下无法稳定运行。原因：
1. 选举超时窗口太短，50节点的网络延迟超过超时窗口
2. 0.25核CPU对50个peer的连接维护和选举处理能力不足
3. 大规模单Raft组本身不是推荐架构（生产环境建议3-7节点/组）

### 2.4 风险等级: 中（架构极限测试，非生产配置）

## 三、TCX-Ⅱ-2：半集群大屠杀（同时强杀多数派节点）

### 3.1 测试配置
- 基于TCX-Ⅱ-1的50节点集群
- 操作: 同时kill -9掉28个节点（N23-N50）
- Quorum=26, 存活22 < 26 → Quorum被击穿

### 3.2 测试结果
- **强杀耗时**: 31.8秒
- **存活节点**: 22/50
- **Quorum状态**: 22 < 26, Quorum击穿 ✅
- **降级行为**: ✅ 所有存活节点进入Follower状态，leader字段为空
  - 无Leader选出 → 写入被拒绝（等效只读降级）
  - term继续增长（482-495），选举尝试但无法成功
- **恢复尝试**: 重新拉起28个节点
  - 全部被OOM Killed（Exit 137）
  - 系统内存15.4GB无法支撑50个容器同时运行
  - 每容器实际使用约20MB，但Docker总开销超过系统限制

### 3.3 分析
1. Quorum击穿后系统正确进入无Leader状态，拒绝写入 ✅
2. 大规模节点恢复需要分批进行，不能一次性拉起所有节点
3. 15.4GB系统内存的硬限制导致50容器恢复失败

### 3.4 风险等级: 低（灾难恢复测试，系统行为符合预期）

## 四、TCX-Ⅱ-3：高频滚动重启下的状态机修复

### 4.1 测试配置
- 节点数: 5（Quorum=3）
- 资源限制: --cpus=0.5 --memory=512m 每节点
- 镜像: raftkv-gateway:v22s
- 操作: 每30秒重启一个节点，连续滚动重启所有5个节点

### 4.2 测试结果
- **初始状态**: N1=Leader(term=2), N2-N5=Follower, peers=5 ✅
- **滚动重启过程**:

| 步骤 | 重启节点 | 重启前状态 | 重启后Leader迁移 | state.bin | wal文件 |
|------|---------|-----------|-----------------|-----------|--------|
| 1 | N1 | Leader(term=2) | → N3 | ✅ 存在 | ✅ wal-000001.log |
| 2 | N2 | Follower(leader=N3) | N3继续 | ✅ 存在 | ✅ wal-000001.log |
| 3 | N3 | Leader(term=4) | → N1 | ✅ 存在 | ✅ wal-000001.log |
| 4 | N4 | Follower(leader=N1) | N1继续 | ✅ 存在 | ✅ wal-000001.log |
| 5 | N5 | Follower(leader=N1) | → N5 | ✅ 存在 | ✅ wal-000001.log |

- **最终状态**: N5=Leader(term=6), N1-N4=Follower, peers=5 ✅
- **state.bin丢失**: 0/5（无丢失）✅
- **Candidate卡死**: 0/5（无卡死）✅
- **Leader迁移链**: N1→N3→N1→N5（自动选举，无人工干预）✅

### 4.3 分析
5节点集群在滚动重启场景下表现优异：
1. 每次重启后state.bin和WAL文件都完整保留 ✅
2. Leader自动迁移到健康节点，无需人工干预 ✅
3. 没有节点卡在Candidate状态 ✅
4. term从2增长到6，仅触发4次选举（5次重启中1次未触发选举）

### 4.4 风险等级: 无（测试全部通过）

|------|--------|--------|------|

3. **授权拦截器轻量**: IsDegradedMode()仅做读锁+布尔检查，开销极小 ✅
4. **延迟可控**: P99=280ms, Max=806ms，无无限增长 ✅
5. **RSA验签**: VerifyLicense()仅在启动时执行一次，运行时不重复验签 ✅

## 七、关键发现汇总

### 7.1 正面发现（系统优势）
1. **5节点集群稳定性**: 滚动重启、Leader迁移、状态保持全部正常（TCX-Ⅱ-3）
2. **Pipeline背压安全**: 1000并发混合读写5分钟，fallback=0，无数据丢失（TCX-Ⅱ-4）
3. **WAL可靠性**: 高压下walErr=0，无WAL错误（TCX-Ⅱ-4）
4. **授权高压安全**: 1000并发下CPU/内存无雪崩（TCX-Ⅱ-5）
5. **Quorum降级正确**: 击穿Quorum后正确进入只读降级（TCX-Ⅱ-2）
6. **无脑裂**: 所有测试中未出现多个Leader同时存在

### 7.2 风险发现（需关注）
1. **50节点选举风暴**: 单Raft组50节点在150-300ms选举超时下无法稳定（TCX-Ⅱ-1）
   - 建议: 生产环境使用3-7节点/组，或调大选举超时
2. **大规模恢复OOM**: 50容器同时恢复时系统内存不足（TCX-Ⅱ-2）
   - 建议: 分批恢复节点，每批10-15个
3. **V2.4选举不稳定**: 3节点V2.4镜像在1000并发下term=1600+（TCX-Ⅱ-4）
   - 建议: 优化V2.4的选举超时或心跳间隔
4. **Max延迟20s**: 混合读写压测中少数请求延迟20秒（TCX-Ⅱ-4）
   - 建议: 增加客户端超时重试机制

### 7.3 架构建议
1. **推荐生产配置**: 3-5节点/Raft组，每节点1核/1GB内存
2. **选举超时**: 建议根据节点数动态调整，N节点建议electionTimeout ≥ N×10ms
3. **恢复策略**: 大规模节点恢复应分批进行，每批不超过系统内存/512MB个节点
4. **监控指标**: 重点监控term增长率（>10/秒表示选举风暴）和Pipeline healthy状态

## 八、测试结论

### 8.1 商业交付评估
- **5节点配置（推荐生产配置）**: ✅ 完全可用，滚动重启稳定，状态不丢失
- **授权系统**: ✅ 高压下无雪崩，商业交付安全
- **Pipeline/WAL**: ✅ 背压安全，无数据丢失风险
- **灾难恢复**: ✅ Quorum击穿后正确降级，拒绝写入

### 8.2 已知限制
- 50节点单Raft组不推荐（选举风暴）→ 使用多Raft组架构

- 大规模恢复需分批 → 运维SOP中明确

### 8.3 最终判定
**V2.2-S镜像在3-5节点配置下完全满足商业交付标准。授权系统、Pipeline背压、WAL可靠性、灾难降级全部通过极限验证。**
