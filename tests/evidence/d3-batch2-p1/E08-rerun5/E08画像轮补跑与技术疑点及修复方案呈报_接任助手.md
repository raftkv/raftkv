## 3. 步骤3 技术疑点答复

### 疑点1：sendHeartbeats 是否全节点运行？
**否，仅 Leader**。
- raft.go:725（赢得选举 `state=StateLeader`）→ raft.go:752 `go rn.heartbeatLoop()`（心跳循环仅 Leader 启动）
- raft.go:285-300 / 797-799 失 Leader 时 `heartbeatStop` 停止心跳
- raft.go:860 sendHeartbeats 首行 `if rn.state != StateLeader { return }`（双保险）

### 疑点2：压测客户端是否打全部 5 节点？
**否，只打 Leader（带 NotLeader 重定向）**。cmd/e04_loadtest/main.go：
- L95-104 `findLeader()`：启动遍历 -nodes 找 `"state":"Leader"`
- L141-143 写请求仅 `POST http://localhost:<leader>/raft/propose`
- L156-165 修复E：收到 "not leader" → `parseLeaderFromError` 切换新 Leader 重试（≤3 次）；压测输出 `重试: 146` 佐证切换发生但量小

### 疑点3："只有 Leader 拷贝" vs "5 节点同涨" 解释链（补齐）
**实测确认 5 节点同涨**（表 2c），Leader=node-1 期间 node-3/node-4 反而更高。解释链四段：
1. **Leader 主放大器**：心跳全量拷贝（raft.go:872-873）O(N)×20/s + Propose 自旋（raft.go:1047 每 20ms 调 sendHeartbeats）——Leader 节点分配风暴（node-1 实测攀升至 1.57GB）。
2. **Follower 独立分配路径（补足，此前报告低估）**：follower 经 AppendEntries 同步（raft.go:1322 append）+ 提交后 fireOnCommit → OnCommit（raft_pipeline.go:253-290：json.Marshal + SM4-CTR 加密 + WAL Append + 每 1 万条 Snapshot 全量 ReplayAll）——**每个 follower 各自执行全套路径**，产生与日志量同级的持续分配。
3. **Leader 漂移放大**：Leader 内存高压 → GC 停顿 → 心跳超时 → 选举 → 新 Leader（带 ~20 万条日志）上任重启拷贝风暴 → 峰值在节点间轮转（对应 2c 的轮转形态）。残留集群 term=5194 佐证历史压测轮次大量切主。
4. **GC 堆扩张共性**：所有节点共享同一 WSL2 VM（15.62GiB），GC 压力联动推高整机内存水位；容器无 mem_limit，OOM 由 VM 级内核在 ~30min 后触发（本次 20min 未达临界，与 E08 30min 五连败同构）。

**中间态观察局限**：逐节点 curl 存在秒级时序差（写 ~185/s），5 节点 commit 读数不同刻不可直接比较；压测停止后 5 节点 commit 收敛一致（221,576）证明数据一致性无问题。

## 4. 步骤4 缺陷B修复方案呈报（只呈报，未动代码）

### 4a. 方案矩阵
| 方案 | 机制 | 评价 |
|---|---|---|
| **B1 Propose 去自旋（必做）** | raft.go:1047 移除 `rn.sendHeartbeats()`，改条件变量/commitNotify 通道唤醒（commitIdx 推进处 signal） | 消灭写请求对心跳的最大放大；改动单文件单点；共识语义零变化 |
| **B2 心跳去全量拷贝（必做）** | raft.go:872-873 删除 `make+copy`，RLock 内直接引用 rn.logs 构造 entries（浅引用 Command/SM3Hash 底层） | 拷贝 O(N)→O(增量)；锁内只复制 64B/条 slice header，持锁时间可控 |
| B3 增量发送 | entries 仅发 `nextIdx[p.ID]..最新` | **已生效**（raft.go:902 startIdx=nextIdx），瓶颈在拷贝不在 entries，无需改 |
| B4 拉模式 | follower 主动拉日志 | 协议改动大、触及 gRPC 语义，不推荐（过度设计） |

### 4b. 推荐组合 B1+B2（伪代码草案）
**B1**：RaftNode 增 `commitNotify chan struct{}`（cap 1）；commitIdx 推进处（raft.go L990 附近，持锁内）`select { case rn.commitNotify <- struct{}{}: default: }`；Propose 等待循环改为 `select { case <-rn.commitNotify: ...检查 commitIdx>=index...; case <-timer.C: return timeout }`，删除 20ms 自旋与 sendHeartbeats 调用。

**B2**：sendHeartbeats 内删除 `logSnapshot := make(...); copy(...)`，改为 RLock 期间用 `rn.logs` 直接切片（`startIdx..len(rn.logs)` 锁内构造 `[]*pb.LogEntry`，浅引用 Command/SM3Hash），锁外发 RPC。

### 4c. 改动范围评估
| 维度 | 结论 |
|---|---|
| 涉及模块 | **raft.go 单文件**（Propose 等待 + sendHeartbeats + commitNotify 字段）；gRPC/proto/消息结构零改动 |
| 共识正确性路径 | 触及核心（raft.go 提交/心跳），但 B1/B2 **不改任何协议判定**（选举/回滚/commit 规则/消息内容均不变），只改"等待机制"与"拷贝方式"→ 共识语义零变化 |
| 消息语义影响 | 无（AppendEntries 请求结构与内容不变） |
| 回归要求 | E01-E03（崩溃/分区/并发确定性）+ F01-F16 + 修复后画像轮对照（期望：同参数 20min 无 GB 级、峰值回落至 <500MB 量级） |
| 缺陷A联动 | B2 后拷贝成本 O(增量)，缺陷A（rn.logs 驻留 ~150B/条）降为次要项；仍按批复暂缓、B 验证后单独批次 |
