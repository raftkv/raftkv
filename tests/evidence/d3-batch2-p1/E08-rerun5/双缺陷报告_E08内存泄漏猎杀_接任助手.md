## 3. 缺陷 A：Raft 内存日志（rn.logs）无 compaction —— 长跑慢性病

### 3a. 定性
已提交的日志条目在 `RaftNode.logs` 中**永久驻留**，全项目无任何日志前缀压缩（InstallSnapshot/compact）机制。WAL 磁盘有快照截断，但**内存日志无截断**。

### 3b. 证据链（文件+行号）
| 证据 | 位置 | 原文/事实 |
|---|---|---|
| logs 字段 | raft.go:64 | `logs []RaftLog // 日志条目（索引从 1 开始，0 为哨兵）` |
| Leader 追加 | raft.go:1034 | `rn.logs = append(rn.logs, entry)`（Propose 内，Leader 本地） |
| Follower 追加 | raft.go:1322 | `rn.logs = append(rn.logs, RaftLog{...})`（AppendEntries 接收） |
| 成员变更追加 | membership.go:226/280 | `rn.logs = append(...)` |
| **唯一"截断"** | raft.go:1317 | `rn.logs = rn.logs[:entry.Index-1]` —— 仅 follower 遇到 **term 冲突**时回滚冲突段，**不压缩已提交前缀** |
| WAL 回放赋值 | raft.go:235-238 | `rn.logs = logs[:validUntil]` / `rn.logs = logs`（仅启动时） |
| RaftLog 结构 | types.go:49-54 | `Index/Term/Command/SM3Hash`（4 字段） |
| WAL 磁盘快照 | raft_pipeline.go:268 | `if p.snapshotThreshold > 0 && p.totalCommitted >= p.snapshotThreshold` → `p.storage.Snapshot()`（阈值 10000，**只重置磁盘 WAL 文件，不截断 rn.logs 内存**） |
| CompactWAL | compact_wal.go | `cw.file.Write(buf)` 只做连续 Term/Index 编码压缩，**只增不截** |

### 3c. 当前速率测算（活体实测）
- 当前存活节点（压测后空载遗留）：`log_count=55753, commit_index=55707`（/raft/status 实测）。
- 即 E08 压测残留 + 启动日志已达 **5.5 万条驻留内存**，且无 Leader（term 持续增长 5027→5194，两存活节点互选打转）。
- E08 16GB 轮：30min 成功 3,218,940 请求 × 20% 写 ≈ **64.4 万条**新增 → 峰值 rn.logs ≈ 70 万条/节点。
- 单条 RaftLog 内存：64B 结构 + Command（~50B 实测 body）+ SM3Hash（32B）= **~146B/条**。
- 驻留量：70 万 × 146B ≈ **105MB/节点**。缺陷 A 自身 **不是 GB 级主犯**，但为缺陷 B 提供线性增长的拷贝基数 N。

### 3d. 修复方案草案（仅建议，批复前不动手）
1. 引入 InstallSnapshot：Leader 定期对已提交前缀生成快照、发送给落后 follower，双方截断 `rn.logs[:snapshotIdx]`。
2. 或最小侵入：在 `commitIdx` 超过阈值（如 5 万）时，将 `rn.logs = append([]RaftLog(nil), rn.logs[trimIdx:]...)` 收缩，配合索引映射。
3. 改动范围评估：触及 `raft.go`（核心共识路径，日志管理）+ 新增 InstallSnapshot RPC（proto/grpc_server.go）→ **高风险，触及核心共识路径，需单独排期**。

## 4. 缺陷 B：GB 级主犯（已定罪）—— 心跳全量拷贝风暴 + Propose 自旋放大

### 4a. 定罪对象：`sendHeartbeats()` 每心跳全量浅拷贝 rn.logs，且被 Propose 等待循环高频触发

### 4b. 完整证据链
| 证据 | 位置 | 原文 |
|---|---|---|
| 心跳全量拷贝 | raft.go:872-873 | `logSnapshot := make([]RaftLog, len(rn.logs)); copy(logSnapshot, rn.logs)` —— **每次心跳无条件全量浅拷贝 rn.logs** |
| 心跳频率基值 | raft.go:36 / 189 | `heartbeatIntervalMin = 50ms`；启动即 `currentHeartbeatInterval: heartbeatIntervalMin` → **20 次/s** |
| 心跳循环 | raft.go:830-856 | `heartbeatLoop()` ticker 驱动，每周期 `sendHeartbeats()` |
| **Propose 自旋放大** | raft.go:1040-1076 | `for attempt := 0; attempt < 50; attempt++ { rn.sendHeartbeats(); ...; time.Sleep(20ms) }` —— **每个写请求等待 commit 期间每 20ms 主动调 sendHeartbeats**（最多 50 次 ≈ 1s） |
| sendHeartbeats 同步阻塞 | raft.go:914-957 | 每 peer goroutine `client.AppendEntries` 后 `wg.Wait()`，rpcTimeout=500ms（raft.go:44）→ 慢 follower 让拷贝驻留变长 |
| entries 构造 | raft.go:901-912 | `for i := startIdx; i <= len(logSnapshot); i++ { entries = append(...) }` —— nextIdx 落后时构造全量 LogEntry |
| 无内存日志截断 | raft.go:1034/1322 | 见缺陷 A —— N 持续线性增长 |

### 4c. 机制（为何 GB 级、为何暴涨-骤降、为何 30min 临界爆发）
- **分配量 = O(rn.logs 条数 × 64B) × 触发频率**。
- 单次心跳拷贝成本 = N_logs × 64B（RaftLog 元素浅拷贝，Command/SM3Hash 共享底层）。N=70 万时单次 **45MB**。
- 触发频率 = 定时 20/s + **写请求放大**。E08 实测 P99=984ms → 大量慢写请求在 Propose 循环内反复触发 sendHeartbeats；并发写（100 并发 × 20% 写）下多个 goroutine 同时持有 45MB 级拷贝并在同步 RPC 阻塞期（最长 500ms）驻留 → **并发驻留峰值 ≈ 并发慢写数 × 45MB**，可达 GB 级。
- **正反馈雪崩**：rn.logs 增长 → 拷贝变贵 → commit 变慢 → 更多写请求进入自旋循环 → 更多并发拷贝 → GC 压力升高 → follower 响应更慢 → 拷贝驻留更久 → 内存净增长越过临界点 → 3 节点 OOM（exit 137），剩余节点因压力回落稳定 ~144MiB。
- **暴涨-骤降形态**：peer RPC 返回后拷贝释放（GC 回收）→ 骤降；新一批写触发 → 暴涨。5s 粒度采样看到的是 GC 堆锯齿的包络。
- **为何空载不涨**：空载 N=5.5 万恒定，拷贝仅 3.5MB/次 × 20/s = 70MB/s，GC 轻松消化 → 水平线（idle-baseline 证实）。

### 4d. 前任嫌疑机制复核（排除/降级）
| 嫌疑 | 复核结论 |
|---|---|
| WAL 1GB 预分配（raft_wal.go:39/112） | **排除**：`f.Truncate(1<<30)` 为稀疏文件预分配，不产生 anon，无 page cache（file 列实测未涨） |
| WAL batch buffer（raft_wal.go:188-190） | **降级**：batch 上限 256 条即 flush，缓冲 ~KB 级 |
| SM4-CTR 加密 buffer（raft_storage.go:78-97） | **降级**：每日志 4 个小分配（IV 16B + cipher + result），全部短命 GC 可回收，无 sync.Pool 但非驻留 |
| 缺陷 A 日志驻留 | 保留（~105MB/节点），非主犯但提供拷贝基数 |
| EncryptedStorage.Snapshot ReplayAll | **降级**：每 1 万条触发（raft_pipeline.go:268），瞬时 ~MB 级，非主犯 |

### 4e. 修复方案草案（仅建议）
1. **根治**：Propose 等待循环不调 `sendHeartbeats()`。改为由心跳 ticker 自然推进 commit（或 waitgroup/条件变量等待 commitIdx 前进），消除写请求放大。改动 1 处（raft.go:1047）。
2. **次选**：`sendHeartbeats()` 不做全量 `copy`，改为 RLock 内直接引用 `rn.logs` 切片构造 entries（锁内只读，避免拷贝）；或用 `nextIdx` 增量发送。
3. **配套**：心跳间隔下限 50ms→200ms（raft.go:36），缓解拷贝频率。
4. **改动范围评估**：raft.go（核心共识路径，心跳/提交推进）——**中高风险**；不改协议、不改 gRPC 接口则风险可控；需回归 E01-E03 + F01-F16 全套。

## 5. 加法账本（量级收口）

**锚点**（E08-rerun5 fail-report + raw-output 实测）：16GB VM，30min，成功 3,218,940 请求，20% 写，写 TPS ~358/s，峰值 rn.logs ~70 万条/节点，OOM 阈值 ≈ 15.62GiB/3 ≈ **5.3GB/节点**。

| 贡献项 | 类型 | 推算 |
|---|---|---|
| 缺陷 A：rn.logs 驻留 | 驻留累积 | 70 万 × 146B ≈ **105MB/节点** |
| 缺陷 B：心跳拷贝驻留（并发慢写 × 单次拷贝） | 驻留峰值 | 后期单次 45MB（70万×64B）；并发 10-100 个慢写 goroutine → **450MB~4.5GB/节点 瞬时驻留** |
| 缺陷 B：拷贝分配速率 | GC 压力 | 定时 20/s + 写触发（358/s×k）≈ 数百次/s × 平均 ~22MB = **数十 GB/s 峰值分配率** → 堆目标扩张 |
| WAL batch / SM4 buffer / Snapshot | 短命 | <10MB，可忽略 |
| 1GB WAL 预分配 | 稀疏文件 | 0（不占 anon） |

**合计 vs 观测**：
- 驻留型合计 ≈ 105MB + 拷贝驻留 0.45~4.5GB ≈ **0.6~4.6GB/节点** → 与"3 节点各 ~5.3GB 触发 OOM"**同数量级（误差 <1 数量级）**，账本基本闭合。
- 关键洞察：**GB 级暴涨 = 心跳全量拷贝在并发写下的驻留叠加 + GC 堆扩张，不是日志体积本身**。前任"16 万条 × 50B ≈ 8MB 解释不了 GB 级"的困惑，源于把泄漏建模为**驻留型**；实际为**分配/驻留风暴型**。
- **账本缺口**：精确"5 节点合计 >16GB 的临界日志数/并发数"依赖运行时 GC 曲线与 peer 延迟分布，纯静态无法精确复算（profile-baseline.csv 缺失）→ 标注 **量级一致，精确值存在不可消除的不确定性**。无"硬凑"。
