## 2. 三个数

### 数1: OOM 时 rn.logs 理论条数
- node-1 @1020s: **442,724 条**
- node-3 @参考点: **494,373 条**

### 数2: 按 146B/条的驻留估计
- RaftLog 结构: Index(8) + Term(8) + Command header(24) + SM3Hash header(24) = 64B
- Command data: `{"src":"e04-42","idx":442723,"ts":1725901234567890}` ≈ 53B
- SM3Hash data: 32B (SM3 256-bit)
- 合计: 64 + 53 + 32 = **149B/条**（取用户指定 146B）

- node-1 @442,724条: 442,724 × 146 = 67,541,644 bytes ≈ **64.4 MB**
- node-3 @494,373条: 494,373 × 146 = 72,178,458 bytes ≈ **68.8 MB**

### 数3: 实测 anon
- node-1 @commit=462,614: **2,555,633,664 bytes ≈ 2.56 GB**
- node-3 @commit=494,373: **4,418,240,512 bytes ≈ 4.42 GB**

## 4. 判定

**缺口 39.8x ~ 71.7x >> 5x → 存在未知的驻留放大器**

### 已知放大器（不足以解释 65x）
1. rn.logs 主副本: 1x = 65 MB
2. Go slice 过分配: ~2x = 130 MB
3. WAL 内存缓冲: 未知（需查）
4. gRPC pb.LogEntry 临时拷贝: 应被 GC 回收
5. Snapshot ReplayAll 全量装载: 每 10K commit 一次，每次 ~65MB

### 未知放大器（步骤2 pprof 目标）
- 45 次 Snapshot × 65MB = 2.9GB（若 GC 未回收）
- JSON marshal 临时大对象
- SM4 加密/解密临时缓冲
- 其他未发现的分配路径
