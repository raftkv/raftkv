### 原因分析

R-04修复C的gap告警检测的是**服务端→服务端复制延迟**（Leader视角的follower gap）。E08的失败路径是**客户端→旧Leader**（写请求被拒），不涉及复制延迟：

- node-1(新Leader)视角：所有follower gap=0（心跳正常，复制正常）
- node-3(旧Leader→Follower)视角：不发起复制，无gap
- 客户端写请求失败路径不经过gap检测系统

**结论：R-04修复C gap告警系统未触发，因为E08的失败发生在客户端→服务端路径，而非服务端→服务端复制路径。** gap告警系统设计目标是检测follower掉队（R-04原缺陷），不覆盖客户端写错节点的场景。

**R-04修复C实战首考结论**：gap告警在E08场景下不适用，需另行考虑客户端侧的失败检测机制。

### 环境差异分析

V2.1长稳0失败跑在**裸金属+本地回环**环境：
- 5节点在同一服务器上通过localhost通信，**无Docker bridge网络层**
- 无外部写入（commit=0），**无leader切换压力**
- 24小时零panic/WARN/ERROR

E08跑在**Docker Desktop+Docker bridge**环境：
- 5节点通过Docker bridge网络通信，有额外的网络栈层
- 100并发持续写入，有leader切换压力
- R-04修复A重连循环每8s对所有peer触发（见Q7）

**结论：V2.1和E08环境完全不同。** V2.1的"0失败"不能直接对比E08的"3.4M失败"，因为：
1. V2.1无外部写入→无leader切换→客户端不会写错节点
2. V2.1用本地回环→无Docker bridge网络开销
3. "环境抖动"解释力存疑——Q4已确认E08期间无Docker网络事件，真正的根因是客户端韧性缺口（Q3），与环境无关

## Q7：fix A/B/C交互排查——重连循环在leader切换期间是否有干扰行为

### R-04修复A重连循环运行模式

E08全程(04:00–06:01)所有5个节点的R-04修复A重连循环**每8秒触发一次**，对每个peer执行：

```
[peer-client] R-04修复A: peer node-X 持续失败>5s，强制重连（DNS重解析）
[peer-client] R-04修复A: peer node-X 重连成功（新DNS resolver）
[raft/node-Y] R-04修复A: peer node-X 客户端已更新（重连回调）
```

**每个节点每8s产生12条重连日志（4个peer × 3条/peer），5节点每8s产生60条。**

### 重连循环与leader切换的关系

| 时间 | 事件 | 重连循环状态 |
|------|------|-------------|
| 04:09:38 | node-1 state=Follower, leader=node-3 | 每8s重连所有peer |
| 04:09:39 | node-1 选举超时→Candidate→赢得选举 | 重连循环仍在运行 |
| 04:09:48 | node-3 state=Follower, leader=node-1 | 重连循环仍在运行 |
| 04:10–06:01 | 稳定运行 | **重连循环持续每8s触发** |

### 干扰分析

R-04修复A重连循环的"持续失败>5s→重连成功"模式表明：

1. **peer连接持续失败**：gRPC连接在建立后5s内即失败，重连成功后5s又失败，循环往复
2. **可能原因**：Docker bridge网络下gRPC keepalive与连接管理存在兼容性问题，导致连接状态在IDLE/READY间反复震荡
3. **对Raft RPC的影响**：每次重连会关闭旧ClientConn创建新ClientConn，期间RPC调用可能失败。如果心跳RPC恰好在重连窗口内发出，follower收不到心跳→选举超时
4. **node-1在04:09:39触发选举超时**：可能是重连循环在04:09:35-04:09:39窗口内干扰了node-3→node-1的心跳传递

**结论：R-04修复A重连循环在E08期间持续运行(每8s触发)，可能干扰Raft心跳RPC导致node-1选举超时。** 但重连循环不是3.4M失败的直接原因——直接原因是客户端无重定向(Q3)。重连循环是leader切换的**可能诱因**，客户端韧性缺口是**失败放大的根因**。

### R-04修复A/B/C交互排查总结

| 修复 | E08期间行为 | 与E08失败的关系 |
|------|------------|-----------------|
| 修复A(重连循环) | 每8s触发，持续全程 | 可能诱因：干扰心跳→选举超时→leader切换 |
| 修复B(degraded标记) | 未触发 | 无关：follower未掉队，gap=0 |
| 修复C(gap告警) | 未触发 | 无关：失败在客户端→服务端路径，非复制路径 |
| 修复D(别名固定) | 生效 | 无关：别名未丢失 |

## 修复建议（待用户审批，本次不实施）

### 优先级P0：客户端Leader重定向（直接根因）

```
收到"not leader: current leader is X"响应后：
1. 解析新leader地址X
2. 更新leaderAddr = X
3. 重发当前请求
4. 记录重定向事件
```

### 优先级P1：客户端请求重试+退避

```
请求失败后：
1. 最多重试3次
2. 指数退避: 10ms, 50ms, 200ms
3. 3次仍失败则计数totalFail++
```

### 优先级P2：R-04修复A重连循环退避（诱因）

```
重连循环优化：
1. 连接失败检测间隔从2s调整为5s
2. 持续失败阈值从5s调整为15s
3. 重连成功后重置失败计数器
4. 添加重连频率限流：同一peer最多每30s重连一次
```

### 优先级P3：服务端返回HTTP 307重定向

```
/raft/propose handler在非leader时：
返回 HTTP 307 Location: http://新leader:端口/raft/propose
而非 HTTP 200 + {"success":false}
```

## 总结

E08 2h长稳3,417,632次失败的根因是**客户端韧性缺口**：客户端在启动时findLeader()找到node-3后，整个2h期间固定写localhost:9003。t=517s时leader从node-3切换到node-1（诱因为R-04修复A重连循环可能干扰心跳），node-3降级为Follower。此后6,675秒内所有写请求持续发往node-3，均返回"not leader"错误，客户端仅计数失败而不重定向，累积3.4M失败。
