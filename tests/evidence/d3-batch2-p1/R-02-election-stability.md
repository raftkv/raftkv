## 2. 选举保护机制（handleElectionTimeout, raft.go:490-560）

| 条件 | 行为 | 超时重置 |
|------|------|---------|
| 当前是Leader | 直接返回 | 不重置 |
| WAL重放未完成 | 拒绝选举 | ×2 (2-4s) |
| WAL门禁关闭 | 拒绝选举 | ×2 (2-4s) |
| 无peer | 不发起选举 | ×10 (10-20s) |
| 日志未追上Leader + 心跳<5s + 失败<3次 | 跳过选举 | ×3 (3-6s) |
| 连续3次选举失败 | 强制突破logCaughtUp | 正常 (1-2s) |

## 3. 5节点拓扑评估

### 3.1 E01b实测

- Leader崩溃→新Leader当选耗时: **<5s**（E01b实测）
- 选举超时1-2s + RequestVote RPC 500ms + quorum收集 < 3s
- 5节点quorum=3，选举通常1轮完成

### 3.2 风险依据对照

| 场景 | 节点数 | 结果 | 来源 |
|------|--------|------|------|
| 5节点 | 5 | 稳定（E01b PASS） | D3-batch1 Part2 |
| 50节点 | 50 | 选举风暴, 写入成功率0% | TCX-Ⅱ-1 (kunpeng-evidence/07) |

**50节点风暴根因**（TCX-Ⅱ-1报告）：选举超时窗口太短，50节点的网络延迟超过超时窗口。

### 3.3 评估结论

| 项 | 结论 |
|---|------|
| 5节点选举超时1-2s | **合理**，quorum=3，1轮选举完成 |
| 选举保护机制 | **完善**，含WAL/日志追平/风暴自愈多重保护 |
| E01b <5s | **达标**，无需调整 |
| 50节点扩展风险 | 选举超时需随节点数增长（batch2 E06规模阶梯验证） |
| 修复建议 | **无需修复**，5节点拓扑下选举参数合理 |

## 4. 与R-01的关联

R-01中node-2的选举风暴（28次/35s）不是选举参数问题，而是gRPC重连退避导致node-2收不到心跳。
修复R-01（缩短gRPC重连退避）后，node-2能快速收到心跳，不会触发选举超时，风暴自然消除。
